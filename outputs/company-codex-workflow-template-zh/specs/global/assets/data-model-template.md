## 表关系总图

这张图回答：权威对象如何关联、跨域链路在哪里汇合、哪些关系不能反向覆盖？

```mermaid
flowchart TB
    subgraph APP["应用域"]
        PROJECT["项目主表<br/>project"]
        CONFIG["配置版本<br/>project_config_version"]
        RESULT["用户可见结果<br/>business_result"]
        PROJECT -->|project_id| CONFIG
        PROJECT -->|project_id| RESULT
    end
    subgraph DOMAIN["业务/算法域"]
        SESSION["运行上下文<br/>session"]
        BATCH["结果版本<br/>result_batch"]
        DETAIL["结果明细<br/>result_detail"]
        SESSION -->|session_id| BATCH
        BATCH -->|result_batch_id| DETAIL
    end
    CONFIG -.->|稳定业务编码，逻辑关联| SESSION
    DETAIL -.->|按相同项目、日期和版本聚合| RESULT
```

关键结论：

- 项目和配置是应用域权威，运行上下文和明细是业务域权威。
- 跨域使用稳定业务编码或显式映射，不建立无法维护的跨库物理外键。
- 两条链只在服务聚合层汇合，不能互相复制并冒充对方权威事实。

## 数据形成时序

这张图回答：数据从初始化到用户查询，分别由谁读取、校验和写入？

```mermaid
sequenceDiagram
    actor Operator as 业务操作人
    participant App as 应用服务
    participant AppDB as 应用域
    participant Domain as 业务/算法服务
    participant DomainDB as 业务/算法域
    Operator->>App: 初始化项目与配置
    App->>AppDB: 写入项目和不可变配置版本
    App->>Domain: 发布稳定项目/配置引用
    Domain->>DomainDB: 创建运行上下文
    Domain->>DomainDB: 写入带版本的结果和明细
    App->>DomainDB: 按明确版本读取业务事实
    App->>AppDB: 读取项目、权限和外部结果
    App-->>Operator: 聚合用户可见结果
```

关键结论：

- 初始化先固定项目与配置，再创建运行上下文。
- 结果修正产生新版本，不原地覆盖已发布事实。
- 页面查询必须使用同一项目、日期、上下文和结果版本。
