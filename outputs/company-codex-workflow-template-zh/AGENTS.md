# Codex 公司项目工作流

这些说明定义本项目中的 Codex 团队工作流。所有变更应保持简单、聚焦、可验证。

## 工作原则

- 优先选择满足已确认需求的最小改动。
- 引入新模式前，先匹配现有项目风格和架构。
- 交付功能或修复问题时，不顺手重构无关代码。
- 当需求、归属或风险不清楚时，明确说明假设。
- 对变化较快的第三方 API，优先使用当前官方文档，不依赖记忆。

## 上下文加载

- 先阅读 `specs/global/INDEX.md`。
- 只阅读与当前任务相关的具体 spec。
- 除非任务明确要求审计或迁移，不要扫描所有 Markdown 文件。
- 如果索引过期，在规划阶段或完成相关 spec 变更后更新索引。

## 目标使用终端契约

- “终端”指 PC Web、移动 Web、App、桌面客户端或大屏等用户使用形态，不是 TCP/HTTP 网络端口。
- 先读取 `specs/global/INDEX.md` 的终端基线，再读取当前需求中的功能例外；只有明确标记“支持”的终端进入设计、任务、实现和验证。
- 未确认移动端时，不得自行增加响应式布局、移动断点、触摸交互、移动端截图、设备矩阵或移动 E2E。
- PC-only 产品只覆盖确认的最小视口、浏览器和鼠标/键盘场景；无 UI 功能可判定“无直接终端差异”。
- 已确认终端范围发生变化时触发范围变化熔断，先更新需求、设计和任务并让用户确认，不得在编码中顺手适配。

## 人类优先总结

- 本轮正式完成或阶段收尾、用户明确索要进度总结、阻塞结论或下一步方案，以及包含审计字段的成段用户回复，都必须先说业务结果和影响，再说风险与下一步；不得从 Workflow Audit、任务 ID、验证等级或内部术语开始。
- 1-2 句的工作中更新和普通问答始终不触发固定格式，即使提到当前结果、风险或下一步；但不得在轻量回复中附带完整审计明细。
- 第一层固定使用：`一句话结论`、`这次完成了什么`、`需要你注意什么`、`你现在需要做什么`。没有风险时直接写“当前没有需要你处理的风险”。
- 用户要求“详细一点”时，只增加四段正文或 `技术审计附录` 的深度，不得删除、改名或调换四个标题。
- 首次出现的内部术语必须解释，例如“V3（高风险验证）”；文件名先说明用途，再给路径。
- 只给一个主要下一步和一句简短可回复话术；备选路径仅在确有分支决策时补充。
- Superpowers、专家调用、命令、路径、哈希、验证证据和内部 workflow 字段放入 `技术审计附录`。不得把内部 workflow 字段逐项倾倒到人类摘要。
- 发送前回复门禁：检查四个标题是否齐全且顺序正确、风险是否已翻译为实际影响、是否只有一个主要下一步；任一不满足时先重写再发送。

## 文档职责和编号

- 写入任何项目文档前，先确认文档角色、信息层级、编号命名空间和更新触发条件。
- `说明文档.md` 或等价入口页只写项目入口、当前状态、最近重要事件和阅读路线，不承载 spike 现场流水。
- Spike 日志使用 spike 内部编号，例如 `SPK02-T001`；正式任务使用 feature、版本或正式任务编号；不要跨文档复用裸 `任务 001`。
- `specs/global/INDEX.md` 应维护文档职责地图。

## 资产落点门禁

- 新增或移动目录、包、Schema、Fixture、测试、脚本、迁移或跨模块共享资产时，先读取 `.codex-workflow/asset-boundaries.json`。
- `specs/` 和 `docs/` 默认只承载文档；被构建、执行、测试或发布的文件进入所属工程。机器契约例外必须在配置中声明所有者和验证方式。
- 设计阶段输出资产归属表；任务阶段写仓库相对完整路径、允许根目录和禁止根目录，不使用含糊短路径。
- 实现或 bugfix 第一次编辑前运行计划路径检查；交付收口只检查本次新增和移动文件。阻断项必须回到设计或规划处理。
- 配置缺失时运行 `generate-asset-boundaries`；自动生成草案由用户确认。pre-commit/CI 强制检查当前暂缓。
- 存在 `asset-boundaries.generated.json` 时，新增或移动工程资产前必须审阅并使用 `accept-asset-boundaries` 采纳，或明确丢弃候选；不得继续依赖已知过期的正式配置。

## 阶段边界

- 需求澄清阶段产出验收标准和边界条件，不编辑生产实现代码。页面/交互验证只能修改 `.codex-workflow/prototypes/<feature>/draft/` 下的隔离、模拟数据原型。
- 技术设计阶段产出架构、API/数据契约、风险说明和测试策略，不编辑实现代码。
- 实现阶段只在需求和设计确认后开始，除非用户明确使用 `/spike` 或 `/hotfix`。
- 原型确认只授权转为权威需求同级 `prototype/` 下的需求基线；用户未明确要求时，不进入技术设计或任务拆分。
- 真实 API、数据库、认证、生产数据/组件、后端、数据库结构、基础设施、性能或技术可行性请求会终止需求原型并重新路由。
- 模糊的“确认”“继续”“下一步”表示继续当前阶段，不表示直接进入设计或编码。

## 阶段一致性预检

- 实现、bugfix 或 hotfix 前，先轻量检查 `说明文档.md`、`specs/global/INDEX.md`、当前 feature/version README、任务文档和相关 public-doc patch 是否一致。
- 如果入口页、索引和任务文档指向不同阶段，普通实现/bugfix 先暂停并修正文档路由。
- 生产 hotfix 可先止血，但完成报告必须记录冲突和补偿文档任务。

## 第一性原理和对抗式审查

- 复杂需求、技术设计、bugfix 根因和 spike 结论前，执行第一性原理检查：底层事实、关键约束、最小成立条件。
- 实现完成、bugfix 完成、hotfix、spike 结论和上线前验证时，执行对抗式审查：极端输入、异常状态、权限绕过、并发重试、未来时间、缓存假阳性、性能或 UI 渲染压力。
- 普通小改动可以跳过，但必须说明原因。
- 不要只写“已检查”；必须给出具体事实、反例场景或跳过理由。

## 标准交接口令

- `需求已确认，进入技术设计`：从需求进入技术设计。
- `方案已确认，开始实现`：从设计进入实现。
- `开始 bugfix`：进入根因分析和修复。
- `/spike <问题>`：进入限时技术探索。
- `/hotfix <事故>`：进入紧急修复。

## 范围变化熔断

- 实现授权只对已确认的需求、设计和任务范围有效。
- 如果实现中发现遗漏架构层、数据加工层、表、接口边界、业务规则、字段口径或文档需要同步更新，旧授权立即失效。
- 熔断后只允许补需求、设计、任务、字段映射或公共文档影响补丁，并输出 `实现授权状态：已失效，需要用户确认后再编码`。
- 不得在补完文档后顺手继续写代码；必须等用户重新确认实现范围。

## 验证规则

- 项目有测试框架时，功能交付应包含可执行测试。
- Bug 修复应先复现或解释失败原因，再改代码。
- 完成声明必须引用实际执行的验证命令或手工检查。
- 如果无法自动验证，提供聚焦的手工检查清单。

## 验证等级和文档漂移

- 自动判定验证等级：`V0` 纯文档或无行为变更；`V1` 低风险小改动；`V2` 标准功能或普通 bugfix；`V3` 生产、权限、安全、数据、性能、金额/指标公式、跨系统或 hotfix。
- 实现、bugfix 和 hotfix 完成前，必须输出验证等级、验证证据、未验证项和剩余风险。
- 如果代码改变了需求承诺、操作逻辑、计算口径、API 契约、技术设计、任务计划或公共入口，必须说明文档漂移影响，并补文档或标记待确认。

## 中文代码逻辑备注

- Java、前端 TypeScript/Vue/React、Python、SQL 和脚本都适用同一备注标准。
- 业务规则、公式阈值、精度、字段映射、枚举/区域映射、fallback/隐藏/降级、异常处理、兼容策略、性能/并发/缓存等非显然逻辑，必须补中文备注。
- 不写“遍历列表”“设置变量”这类语法翻译备注。
- 阈值、公式或映射来源不清时，先补需求或业务规则文档，不用备注替代缺失口径。

## 例外通道

- `/spike` 可以跳过完整 SDLC 文档，但必须产出简短 spike 报告。
- `/hotfix` 可以优先恢复服务，但必须产出 hotfix 报告和后续测试债务。
- 例外工作应最小化、隔离，并在事后进入正常清理规划。

## 触发式质量验收

- V0/V1 默认跳过；多任务或跨边界 V2 进入 `company-quality-validation`；里程碑、版本、V3 和 hotfix 补偿强制进入。
- 结果为通过、有条件通过或阻断。阻断进入 bugfix 后重验；有条件通过必须由用户显式接受。
- 独立验收不修改生产代码；强制验收未通过时不得进入交付收口。

## Fixture 到真实 API 的交付边界

- Fixture 或 Mock 只用于前端开发过渡；本地验证最多标记 `FIXTURE_READY`。
- 需要真实 API 而联调未完成时标记 `API_PENDING`，质量验收保持阻断；有条件合入不等于有条件通过。
- 只有用户明确批准后，才可把候选标记为 `CONDITIONAL_MERGED` 并合入普通业务分支。必须记录批准人、批准时间、目标业务分支、到期条件和补偿任务。
- 有条件合入不代表验收、交付、发布、部署或真实数据正确，生产路径不得静默回退到 Fixture 或 Mock。
- API 恢复后必须完成真实联调和独立验收，达到 `API_INTEGRATED` 与 `QUALITY_PASS` 后才能正式交付。

## 人类可读正式文档

- 新建或重写正式文档前，先读取 `specs/global/assets/document-standard.md`。
- 阅读顺序统一为：先看结论 -> 再看图 -> 再看关键表格 -> 最后看细节与证据。
- 正式文档必须包含 `work-item-id` 和类型化 Mermaid 图；只有用户明确说明不需要图表时才能记录 `图表豁免`。
- 新文档执行 `DOC-G01` 至 `DOC-G12`；历史文档只渐进修复本次修改范围。
