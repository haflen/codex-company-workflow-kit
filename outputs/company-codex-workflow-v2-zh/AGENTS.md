# 公司 Codex 工作流

本项目使用轻量 SDLC。目标是让需求、设计、实现和验证可追溯，同时不拖慢简单工作。

## 上下文优先

- 规划或编辑前，先阅读 `specs/global/INDEX.md`。
- 如果存在 `说明文档.md` 或等价进度文档，读取当前进展和项目状态。
- 只读取当前版本、里程碑、功能文档和相关源码。
- 除非任务是审计或迁移，不要扫描所有 Markdown 文件。

## 目标使用终端契约

- “终端”指 PC Web、移动 Web、App、桌面客户端或大屏等用户使用形态，不是 TCP/HTTP 网络端口。
- 先读取 `specs/global/INDEX.md` 的终端基线，再读取当前需求中的功能例外；只有明确标记“支持”的终端进入设计、任务、实现和验证。
- 未确认移动端时，不得自行增加响应式布局、移动断点、触摸交互、移动端截图、设备矩阵或移动 E2E。
- PC-only 产品只覆盖确认的最小视口、浏览器和鼠标/键盘场景；无 UI 功能可判定“无直接终端差异”。
- 已确认终端范围发生变化时触发范围变化熔断，先更新需求、设计和任务并让用户确认，不得在编码中顺手适配。

## 人类优先总结

- 最终回复先说业务结果和影响，再说风险与下一步；不得从 Workflow Audit、任务 ID、验证等级或内部术语开始。
- 第一层固定使用：`一句话结论`、`这次完成了什么`、`需要你注意什么`、`你现在需要做什么`。没有风险时直接写“当前没有需要你处理的风险”。
- 首次出现的内部术语必须解释，例如“V3（高风险验证）”；文件名先说明用途，再给路径。
- 只给一个主要下一步和一句简短可回复话术；备选路径仅在确有分支决策时补充。
- Superpowers、专家调用、命令、路径、哈希、验证证据和内部 workflow 字段放入 `技术审计附录`。不得把内部 workflow 字段逐项倾倒到人类摘要。

## 工作流文档职责

写入任何项目文档前，必须先确认文档角色、信息层级、编号命名空间和更新触发条件。不要把项目入口摘要、spike 现场流水、正式需求/设计/任务和生命周期总结混成同一条任务链。

默认职责：

- `说明文档.md` 或等价入口页：项目入口、当前状态、最近重要事件、阅读路线。不要承载 spike 现场流水，不使用 spike 内部任务号。
- `spike_*_工作日志.md` 或 spike 目录日志：spike 现场流水、实验过程、临时结论。使用 spike 内部编号，例如 `SPK02-T001`，不要使用裸 `任务 001`。
- `specs/versions/...` 或 `specs/features/...`：正式需求、设计、任务计划和验收依据。使用 feature、版本或正式任务编号，不继承 spike 流水号。
- `docs/lifecycle/`：版本生命周期阶段总结和里程碑回顾，只写阶段性摘要，不追逐每个小任务。
- `specs/global/INDEX.md`：文档职责地图和路由索引，是判断该写哪个文档的入口。

更新触发：

- 项目入口页只在当前阶段、最近重要事件、阅读路线或关键状态变化时更新。
- Spike 日志只在 spike 实验、观察、决策或临时任务变化时更新。
- 正式 specs 只在需求、设计、任务、验收或正式变更被确认时更新。
- 生命周期文档只在版本阶段结束、里程碑变化或需要管理层摘要时更新。

发现同一裸编号出现在不同层级文档时，必须先暂停写入并建议改成带命名空间编号，例如 `SPK02-T183`、`FEAT-DT-T01` 或日期型项目事件。

## 多分支公共文档协议

多分支并行时，公共入口文档默认代表主线事实，不代表某个开发分支的局部状态。

- `说明文档.md`、`specs/global/INDEX.md` 等公共主线文档默认只在 `main`、`master`、`develop`、`integration` 或明确的集成分支更新。
- feature、spike、hotfix 分支默认不直接把未合并内容写入公共文档的“当前状态”。
- 分支如果影响项目入口、当前阶段、最近重要事件、阅读路线、文档职责或编号规则，应写入 `docs/public-doc-updates/<branch-or-feature>.md`。
- 分支私有过程写入 `specs/features/<feature>/`、`specs/versions/...`、`spikes/` 或对应工作日志，不写进公共入口页。
- 合并阶段统一读取公共文档影响补丁，再把已合并事实升格到 `说明文档.md` 和 `specs/global/INDEX.md`。
- 多个分支修改同一公共段落时，不在业务分支抢改公共文档；先保留各自补丁，由集成分支统一重写公共段落。
- 如确需在业务分支直接改公共文档，必须说明原因，并在完成报告中标记为 `公共文档直接写入风险`。

## 资产落点门禁

- 新增或移动目录、包、Schema、Fixture、测试、脚本、迁移或跨模块共享资产时，先读取 `.codex-workflow/asset-boundaries.json`。
- `specs/` 和 `docs/` 默认只承载文档；被构建、执行、测试或发布的文件进入所属工程。机器契约例外必须在配置中声明所有者和验证方式。
- 设计阶段输出资产归属表；任务阶段写仓库相对完整路径、允许根目录和禁止根目录，不使用含糊短路径。
- 实现或 bugfix 第一次编辑前运行计划路径检查；交付收口只检查本次新增和移动文件。阻断项必须回到设计或规划处理。
- 配置缺失时运行 `generate-asset-boundaries`；自动生成草案由用户确认。pre-commit/CI 强制检查当前暂缓。
- 存在 `asset-boundaries.generated.json` 时，新增或移动工程资产前必须审阅并使用 `accept-asset-boundaries` 采纳，或明确丢弃候选；不得继续依赖已知过期的正式配置。

## 阶段边界

- 需求阶段产出目标、范围、验收标准和边界条件，不编辑生产实现代码。需要页面/交互验证时，只能由 `company-requirements-prototype` 修改 `.codex-workflow/prototypes/<feature>/draft/` 下的隔离、模拟数据原型。
- 设计阶段产出架构、契约、数据流、风险和测试策略，不编辑实现代码。
- 规划阶段产出可执行任务和验证点，不编辑实现代码。
- 实现阶段只在需求、设计和任务确认后开始，`/spike` 和 `/hotfix` 除外。
- 原型确认只授权转为权威需求同级 `prototype/` 下的需求基线；除非用户明确说“进入技术设计”，不得进入设计或任务拆分。
- 真实 API、数据库、认证、生产数据/组件、后端、数据库结构、基础设施、性能或技术可行性请求会终止需求原型，并重新路由到 spike 或已授权设计。
- 模糊的“确认”“继续”“下一步”表示继续当前阶段，不表示进入下一阶段。

## 触发式质量验收

- TDD 属于实现过程反馈；`company-quality-validation` 属于实现后的独立交付验收，两者不得互相替代。
- V0/V1 和证据充分的单任务 V2 默认不进入独立验收；多任务/跨模块/跨边界 V2 进入验收；里程碑、版本、V3 和 hotfix 补偿链路强制进入。
- 用户不需要自己判断。规划输出预计判定，实现或 bugfix 完成时确认最终判定和依据。
- 验收结果只有 `通过 / 有条件通过 / 阻断`；阻断进入 `company-bugfix-runner` 并在修复后重验，有条件通过必须由用户显式接受。
- `company-quality-validation` 不修改生产代码；需求、规则或设计不明确时回到文档阶段。
- `company-delivery-closeout` 必须检查强制验收证据；缺失、过期或阻断时停止 commit/push。

## 交付收口边界

- 任务实现和里程碑交付收口是两个阶段；任务完成报告不能替代收口。
- 所有任务均已完成、明确延期或明确不做后，使用 `company-delivery-closeout`。
- `prepare` 不 commit、不 push；`commit` 只本地提交；`deliver` 才允许普通 push 当前业务分支。
- 未知归属、未完成任务、验证失败、文档冲突、敏感/生产/数据库/异常大文件、受保护分支、staged 清单不一致或普通 push 被拒绝时停止。
- 普通 push 授权不包含 rebase、强制推送、amend、合并、发布或部署。
- 收口只精确暂存已分类文件，不整仓暂存；临时文件只有来源可证明时才能删除。

## 对话交接

- 长对话准备切换、暂停、下次继续或转交任务时，使用 `company-thread-handoff`，先判断 `resume / compact / fork / handoff`。
- 同一任务继续优先 resume；只因上下文过长优先 compact；完整历史不能丢时使用 fork；需要干净上下文时才生成交接胶囊。
- 默认只在回复中输出；仅在用户明确要求时覆盖 `.codex/handoff/current.md`。
- 当前主任务是唯一执行主线；旁支事项标记为未纳入当前范围、未经授权。
- 交接胶囊按 `quick / standard / decision-rich` 分级；涉及产品边界、架构、业务规则、计算、数据、安全或被否方案时使用 `decision-rich`。
- 新对话风险分级核对项目路径、Git 分支、工作区、关键文件、未完成任务和实现授权，并复述目标、决策、约束、状态、未完成事项和授权。
- 只有用户明确要求且目标任务已知时才能 fork 或跨任务发送；必须反馈发送、读取和语义校验状态。
- 项目事实优先于旧交接；交接不替代 `company-context-index` 或正式文档，也不产生新的实现授权。
- Workflow 可以在阶段结束、范围混淆、未提交改动、运行中服务或验证未完成时提醒选择连续性方式，但不得静默写文件或创建任务。

## 连续执行模式

连续执行模式只用于已确认任务清单中的实现阶段，目标是减少重复确认，不是跳过边界。

- 只有用户明确说“继续完成后续所有任务”“连续执行”“批量推进”或等价表达时，才能启用。
- 启用前必须通过阶段一致性预检和范围变化熔断检查。
- 任务计划应标注 `可连续 / 谨慎连续 / 必须停下`。
- `V0/V1` 可连续处理相关任务；`V2` 每次只连续处理 1-3 个强相关任务；`V3` 默认单任务完成后停下确认。
- 每完成一个任务都必须重新检查：范围变化、验证失败、V3 风险、用户确认点、工作区冲突、高权限命令、本机资源异常。
- 命中停止条件时，不得继续下一个任务；输出停止原因、当前证据和推荐下一句。

每个实现、bugfix、hotfix、spike 或文档交接完成后，都必须输出下一步引导：

- `下一步建议：` 继续实现 / 回到需求 / 回到设计 / 任务确认 / 补验证 / 暂停。
- `推荐用户下一句：` 给出用户可以直接复制的下一句。

## Codex 目标追踪

Codex 目标只用于跨轮次目标管理，不替代公司 workflow 的阶段边界。

- L0/L1 小任务默认不建议建立目标。
- L2 标准功能、跨阶段任务、跨会话任务、多文档任务或连续执行模式，建议建立目标。
- L3 高风险任务、旧项目接入、技能升级/安全审查、专家依赖维护、hotfix 后补偿链路，强烈建议建立目标。
- 目标描述必须写最终成功标准，而不是把需求、设计、实现每一步当作目标内容。
- 目标存在不代表实现授权有效；阶段一致性预检、范围变化熔断、V3 停止条件、验证失败和用户确认仍然优先。
- 完成报告应在复杂任务中输出 `目标状态建议`：是否建议建立、保持或关闭 Codex 目标。

## Codex 计划模式

Codex 计划模式用于正式 workflow 前的路线判断，不是新的交付阶段。

- L0/L1 小任务、路径清楚的单点实现或单点 bugfix 默认不建议使用计划模式。
- L2 标准功能但需求仍有歧义、需要方案对比、旧项目接入、范围变化后重新判断路线、连续执行前确认任务顺序时，建议使用计划模式。
- L3 高风险、跨系统、数据、权限、安全、性能、金额/指标公式、生产事故复盘、大迁移或多人协作交付时，强烈建议使用计划模式。
- 计划模式只能输出路线、风险、待确认问题和下一步口令；不得改文件、不得编码、不得替代需求/方案/任务确认。
- 计划模式输出后，必须回到正式公司 workflow：需求、设计、任务拆解、实现、bugfix、hotfix、spike 或技能治理。
- workflow 输出必须包含 `Codex 计划模式建议`，并说明是否建议、原因、提示词和计划完成后的正式 workflow。

## Subagents 使用

Subagents 用于隔离上下文、独立排查、独立执行或独立审查，不是默认执行方式，也不是 App 端的独立按钮入口。

- L0/L1 小任务、单文件小改、纯文档/注释、小 UI 文案、小配置、单一路径 bugfix 默认不使用 subagents。
- L2 多任务交付且任务边界清楚，或多个独立失败域，建议使用 subagents。
- L3 高风险、跨模块/跨系统、数据/权限/安全/性能、复杂旧项目接入、技能升级安全审查或连续执行批次较大，强烈建议使用 subagents，至少用于独立审查。
- Codex 只在用户显式要求 `spawn agents`、`delegate in parallel`、`使用 subagents 并行审查` 或等价表达时启动子代理；workflow 建议本身不等于真实调用。
- Codex CLI 可用 `/agent` 管理 agent thread；Codex App 侧主要展示子代理活动，不要求用户寻找独立的子代理按钮。
- 如需稳定公司角色，先执行 `bash scripts/install.sh install-agents <project-path> --lang zh` 生成项目级 `.codex/agents/`。
- 主 agent 始终负责阶段许可、实现授权、任务分派、diff 复核、验证证据和最终结论。
- 子 agent 只接收窄任务包：目标、边界、允许文件、禁止事项、验证方式和预期输出。
- 不得并行派发会编辑同一文件、同一状态模型、同一数据库迁移、同一公共文档段落的任务。
- 子 agent 输出不能直接作为完成结论；主 agent 必须复核并验证。
- workflow 输出必须包含 `Subagents 建议`、`Subagent 能力状态` 和 `Subagents 实际调用`，像 Superpowers 一样区分真实调用、未调用、需要用户显式请求、需要 custom agents 和仅采用拆分视角。

## 范围变化熔断

实现授权只对当时已确认的需求、设计和任务范围有效。进入实现后，如果用户或 Codex 发现范围发生实质变化，旧的“开始实现”授权立即失效，必须先暂停编码并重新确认阶段。

命中以下任一情况，默认触发 `Scope Change Circuit Breaker`：

- 新增或补漏架构层、数据加工层、表、接口边界、调度链路、外部系统或关键模块。
- 用户表达“遗漏了”“先分析”“为什么”“怎么放入”“补充完善文档”“业务口径还没确认”“需求/设计/任务文档需要同步更新”等意图。
- 当前实现范围超出任务拆解、方案对比、API 契约或 `business-rules.md` 已确认内容。
- 发现字段来源、计算口径、状态流转、异常/降级策略、权限边界或数据同步策略未确认。
- 补文档后出现新的契约、字段映射、任务清单或公共文档影响，而用户还没有确认这些产物。

熔断后允许的动作：

- 只补需求、业务规则、技术设计、任务拆解、字段映射或公共文档影响补丁。
- 输出 `实现授权状态：已失效，需要用户确认后再编码`。
- 给出需要用户确认的范围变化、权威文档和下一步口令。

熔断后禁止的动作：

- 不得把旧的 `任务已确认，开始实现` 继续套用到新增范围。
- 不得在补完文档后顺手继续写代码。
- 不得用专家路由结果替代用户对新范围的实现确认。

## 阶段一致性预检

进入实现、bugfix 或 hotfix 前，必须先做轻量 `Phase Consistency Preflight`，避免公共入口、索引和当前任务文档互相矛盾后才开始编码。

只读取最小必要文档，不做全量 Markdown 扫描：

- 当前分支名和工作区状态。
- `说明文档.md` 或等价项目入口页。
- `specs/global/INDEX.md`。
- 当前 feature、version、milestone 的 README 或任务文档。
- 当前 requirements、design、tasks、business-rules、api-contract，如存在。
- `docs/public-doc-updates/` 中与当前分支或功能相关的补丁。

权威层级：

- 当前任务执行真相优先来自已确认的 feature/version 任务文档。
- `specs/global/INDEX.md` 负责路由和文档职责，不一定代表分支实时状态。
- `说明文档.md` 代表主线入口和当前主线状态，不代表 feature/spike 分支局部状态。
- 非集成分支影响公共入口时，优先写 `docs/public-doc-updates/<branch-or-feature>.md`，不要直接把局部状态写入公共入口。

如果发现阶段、入口、版本、任务编号、当前状态或权威文档冲突，必须先暂停实现并输出：

- `阶段一致性预检：未通过`
- 冲突文件和具体冲突。
- 本轮暂定权威文档。
- 建议修复动作：更新 public-doc patch、修正 INDEX、修正入口摘要、或等待用户确认。

只有预检通过，或用户确认按某个权威文档继续，才进入代码实现或修复。

## 第一性原理与对抗式审查

公司 workflow 内置两类检查，不要求用户每次手动输入提示词：

- `First Principles Check`：回到底层事实、约束和最小成立条件，避免用经验类比替代表层问题的根因分析。
- `Adversarial Review`：从恶意用户、极端数据、异常状态、权限绕过、并发重试、超大输入、未来时间、缓存假阳性和渲染压力等反例角度验证方案。

自动触发规则：

- 需求阶段：L2/L3 或业务规则复杂时，至少写出核心假设、不可破坏约束和反例场景；命中指标、公式、状态流转、复杂操作、字段口径或异常数据处理时，创建或更新 `business-rules.md`。
- 设计阶段：架构、数据、权限、性能、安全、外部 API、前端渲染或跨服务边界不平凡时，必须执行 `First Principles Check`。
- 设计阶段：L2/L3 大功能、核心模块、跨边界、数据模型、权限、安全、性能、业务规则或明显技术取舍场景，必须做 2-3 个方案对比并取得用户确认；L1 小改动可跳过但必须说明原因。
- 规划阶段：每个非平凡任务必须包含最小失败案例或验证锚点，并至少包含一个对抗场景。
- 实现阶段：完成前必须执行 `Adversarial Review`，除非纯文案、注释或无行为小改动，并说明原因。
- Bugfix/hotfix：定位根因前必须执行 `First Principles Check`，完成前必须执行回归和对抗式审查。
- Spike：实验结论前必须写出第一性原理假设、反例实验和证据边界。
- 技能升级、安全审查、自进化提案默认使用 `full-audit`，并执行对抗式审查。

输出要求：

- `第一性原理检查：` 写底层事实、约束、最小成立条件或为什么本轮可跳过。
- `对抗式审查：` 写极端、恶意或异常场景、结果或为什么本轮可跳过。
- 不要只写“已从第一性原理分析”或“已做对抗式审查”；必须给出具体事实或场景。

## Superpowers 可见叠加

- 每个 workflow 输出都必须显式包含 `工作流层`、`Superpowers 叠加` 和 `执行策略`。
- 每个 workflow 开头都必须显式包含 `实际调用`、`专家/插件能力` 和 `未调用但采用视角`，不能只写“专家视角”而不说明是否真实调用 skill。
- 每个 workflow 结尾都必须显式包含 `验证证据`、`未验证项` 和 `剩余风险`。如果本阶段不需要验证，必须说明原因。
- 如果某个 Superpowers、专家 skill、MCP、浏览器或其他 Codex 插件能力没有在当前会话真实暴露或真实调用，必须写入 `未调用但采用视角`，并说明原因。
- 需求探索默认叠加 `superpowers:brainstorming`。
- 复杂任务拆解默认叠加 `superpowers:writing-plans`。
- 实现阶段默认叠加 `superpowers:test-driven-development` 和 `superpowers:verification-before-completion`。
- Bugfix 默认叠加 `superpowers:systematic-debugging`，完成前叠加 `superpowers:verification-before-completion`。
- 如果某个简单任务不叠加 Superpowers，必须明确说明原因。

## 业务规则与计算口径

- `business-rules.md` 只在复杂业务场景触发，不用于纯文案、小 UI、小配置等低风险小改动。
- 触发条件包括：指标/公式/金额/评分/排序/权重/汇总/折算、状态流转、审批/任务流、角色差异、权限规则、字段来源/单位/精度/映射、缺失数据、异常值、批量处理、重复提交、并发冲突。
- 需求阶段负责判定是否需要 `business-rules.md`；如果不需要，必须写明原因。
- 设计阶段只能映射业务规则，不得重新发明公式或口径。
- 任务拆解阶段必须把规则样例转成自动测试或明确手工验证步骤。
- 实现或 bugfix 阶段发现规则缺失时，停止猜测，回到需求阶段补齐规则文档或变更请求。

## 中文代码逻辑备注

AI 编写或修改代码时，默认使用中文补充必要的代码逻辑备注。备注目标是帮助后续审查、交接和业务口径复盘，不是给显而易见的语法逐行翻译。

以下场景必须补中文备注，适用于 Java、前端 TypeScript/Vue/React、Python、SQL、脚本和配置生成逻辑：

- 业务规则、状态判断、审批流、任务流、权限分支或跨角色差异。
- 指标公式、金额、精度、四舍五入、阈值、排序权重、聚合口径。
- 数据源、字段映射、区域/枚举/字典映射、单位换算、前后端 DTO/API 映射。
- fallback、隐藏、降级、空数据、异常值、兼容旧数据或临时过渡策略。
- 非显然的性能、并发、缓存、重试、幂等或浏览器渲染处理。
- 与 `business-rules.md`、API 契约或设计文档中的约束对应的实现点。

禁止写无效备注：

- 不解释语法本身，例如“遍历列表”“设置变量”“返回结果”。
- 不编造业务来源；阈值或公式来源不清时，先回到需求或 `business-rules.md` 补齐。
- 不用备注掩盖复杂代码；能通过命名、拆方法、抽常量表达清楚的，优先改善结构，再补关键说明。
- 修改逻辑时必须同步更新相关备注，避免注释和代码漂移。

实现、bugfix 和 hotfix 完成前必须输出 `代码备注检查：已补充 / 不需要 / 需补充`，并说明覆盖点，例如业务规则、计算口径、数据映射、异常分支、性能策略或没有需要覆盖的点。

## 技术方案对比

- 方案对比是触发式强制，不是全量强制。
- L1 小文案、小 UI、小配置、单一路径低风险改动可跳过方案对比，但必须写明原因。
- L2/L3 命中新模块、核心流程、跨服务/前后端边界、数据模型、权限、安全、性能、缓存、并发、外部 API、业务规则或长期可维护性取舍时，必须比较 2-3 个方案。
- 方案对比必须包含推荐方案、备选方案、主要取舍、风险和用户确认点。
- 命中 L2/L3 方案对比后，未获得用户确认不得进入任务拆解。

## 验证等级与文档漂移

验证等级由 workflow 自动判定，用户不需要手动选择。目标是在风险可控前提下降低 token、时间和本机资源消耗。

- `V0`：纯文档、注释、格式、提示词或无行为变更。验证证据为 diff 检查、目标文件复核或渲染检查。
- `V1`：低风险小行为、小 UI、小配置或单一路径变更。验证证据为聚焦命令、局部测试、手工路径或最小页面检查。
- `V2`：标准功能、bugfix、跨文件行为、API/数据契约或用户可见流程。验证证据为相关自动测试、类型/构建检查和必要的浏览器/手工验证。
- `V3`：生产、权限、安全、金额/指标计算、数据迁移、并发、性能、外部 API、hotfix 或大范围重构。验证证据为回归、对抗场景、回滚/恢复说明和必要的端到端或性能检查。

自动判定规则：

- 纯文档且不改变规范含义时用 `V0`。
- 单点、低风险、可人工确认的小改动用 `V1`。
- 默认功能实现和普通 bugfix 用 `V2`。
- 命中生产、数据、权限、安全、性能、金额/指标公式、跨系统或 hotfix 时升级到 `V3`。

实现、bugfix 和 hotfix 完成前必须输出：

- `验证等级：V0/V1/V2/V3`
- `验证证据：` 写实际命令、检查结果、截图、日志或手工检查。
- `文档漂移影响：` 写是否需要更新 requirements、business-rules、design、api-contract、tasks、`说明文档.md`、`specs/global/INDEX.md` 或公共文档影响补丁。
- `未验证项：` 写未验证原因和建议补验方式。

如果代码实现改变了操作逻辑、计算口径、字段语义、接口契约、验收标准或用户流程，而文档没有同步，不能直接声称完成；必须补文档或明确写入待确认漂移。

## 能力调用透明度

所有公司 workflow 默认使用以下透明度协议，除非用户明确要求极简输出：

### 自动分级

用户不需要判断使用哪种透明度级别；workflow 必须自动判定：

- `light`：默认模式。用于普通阶段内推进、小改动、文档更新、低风险继续工作。只保留必要的实际调用、仅采用视角、验证证据和风险说明。
- `full-audit`：关键节点或异常模式。命中以下任一条件时自动启用完整 `Workflow Audit`：
  - 阶段交接：需求到设计、设计到任务、任务到实现。
  - 实现完成、bugfix 完成、hotfix 任意阶段、spike 结论输出。
  - 技能升级、专家依赖更新、安全审查、自进化提案。
  - 出现“专家/插件未真实调用，只采用视角”。
  - 当前会话缺少应有 Superpowers、专家 skill、MCP、浏览器或插件能力。
  - 验证失败、验证缺失、无法运行测试。
  - 涉及生产、数据、权限、架构、性能或安全风险。
  - 用户要求“审计”“检查流程”“确认是否合规”。

开头：

- `工作流层：`
- `透明度模式：light` 或 `透明度模式：full-audit`
- `实际调用：` 写真实触发或读取的 workflow、Superpowers、专家 skill、MCP、浏览器能力。
- `专家/插件能力：` 写本轮需要或已选择的专家、Superpowers、Codex 插件能力。
- `未调用但采用视角：` 写当前会话不可见、阶段不适合或风险不值得真实调用的能力。
- `Codex 计划模式建议：` 写不需要、建议使用或强烈建议使用，以及原因。
- `Subagents 建议：` 写不需要、建议使用或强烈建议使用。
- `Subagent 能力状态：` 写未检查、当前会话可用、需要用户显式请求、需要本地 custom agents 配置、或当前 App 仅展示活动。
- `Subagents 实际调用：` 写未调用、已调用、仅采用拆分视角、或未调用并给出原因。
- `第一性原理检查：`
- `对抗式审查：`
- `执行策略：`

结尾：

- `验证证据：` 写命令、检查结果、文件变更、截图、日志或人工检查证据。
- `未验证项：` 写未能验证或本阶段无需验证的内容。
- `剩余风险：`

不能用“已按专家视角执行”替代真实调用说明；必须区分 `已真实调用` 与 `仅采用视角`。

`full-audit` 模式额外输出：

- `Workflow Audit：`
- `阶段边界：`
- `Superpowers 声明：`
- `专家/插件真实调用：`
- `仅采用视角：`
- `验证证据：`
- `未验证项：`
- `结论：`

## 专家使用

普通工作不要求用户手动点名专家。工作流应从 `BUNDLES.md` 选择最小匹配组合，再在当前阶段需要时使用对应专家。

如果用户明确点名专家，在不违反安全和项目约束的前提下优先遵循。

第三方 API 或框架行为可能变化时，优先使用官方最新文档。没有 Context7 类 MCP 时，说明限制并使用官方文档或本地包文档。

使用 `company-expert-routing` 作为专家选择入口。使用 `BUNDLES.md` 管理专家组合，使用 `EXPERTS.lock.md` 检查外部专家技能的来源、pin、许可和审查状态。优先读取项目根目录文件；如果项目内缺失，读取插件内置 fallback，不要直接放弃专家路由。

使用模板时优先读取项目内 `specs/global/assets/`；如果项目模板缺失，读取插件内置 fallback，并提醒用户执行 `bootstrap-project` 或 `update-templates` 补齐项目模板。

不要自动更新外部专家技能。采用 `company-skill-upgrade-runner` 获取候选版本、比对新旧内容、安全审查、输出建议，并等待用户明确确认后再覆盖。

自进化默认只产出提案。使用 `company-skill-evolution-lab` 记录重复问题并提出受控改进，不允许 skill 直接自改生产版本。

## 验证

- 功能工作在有测试框架时需要测试。
- Bug 修复在改代码前需要复现或清晰证据链。
- 完成报告必须包含准确验证命令或手工检查。
- 无法自动验证时，提供聚焦的手工检查清单。

## 文档

- 公司项目应维护 `说明文档.md` 或等价进度文档。
- 项目应维护文档职责地图，优先写在 `specs/global/INDEX.md`。
- 不同层级文档不得共享裸任务编号；spike、feature、版本任务和项目事件必须使用不同命名空间。
- 版本化 specs 可使用 `specs/versions/<version>/<milestone>/`。
- 小变更可使用 `specs/features/<feature>/` 下的紧凑 spec。
- 公共 API 和复杂逻辑需要注释；常规函数不需要样板注释。

## 人类可读正式文档

- 新建或重写正式需求、设计、数据模型、业务规则、API 契约、任务、原型确认、spike、hotfix 和交付收口文档前，先读取项目内 `specs/global/assets/document-standard.md`；项目内不存在时读取插件同路径 fallback。
- 默认阅读顺序是：先看结论 -> 再看图 -> 再看关键表格 -> 最后看细节与证据。关键结论不得只藏在表格或 Mermaid 图中。
- 正式文档必须使用 `work-item-id`，并按文档类型带齐对应 Mermaid 图。只有用户明确说明不需要图表时，才能记录 `图表豁免`，不得由 Codex 自行豁免。
- 新文档完整执行 `DOC-G01` 至 `DOC-G12`；历史文档只在本次修改范围内渐进修复，除非用户要求全面重写。
- 工作流 skill 负责检查本阶段门禁，`company-workflow-health-check` 负责诊断整体缺失；不得用章节数或行数代替内容质量检查。
