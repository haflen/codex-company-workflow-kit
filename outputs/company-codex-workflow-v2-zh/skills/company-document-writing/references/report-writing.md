# 汇报写法对照

先判断读者要了解的工作，再选择表达。以下是写法样例，具体业务事实以本次材料为准。

| 用途 | 不合适的写法 | 成稿写法 |
| --- | --- | --- |
| 发布安排 | 系统A负责生成，系统B负责展示，因此页面日期本身不能决定生产什么时候出现记录 | 发布前，双方对齐脚本、执行窗口和首个业务日期；确认后同步上线安排 |
| 页面变化 | 运行数据可看，收益完整性另行判断 | 收益待补时，已形成的运行轨迹仍可查看 |
| 分工协调 | 把所有责任边界展开，再解释哪些结论不能推导 | 算法侧计算并更正结果，应用侧更新历史明细和统计 |
| 图注 | 此图证明测试数据可读，不能推导生产日期必有记录 | 标出图中日期、对象、数值或待补状态；上线条件写在发布安排处 |

汇报中的条件以功能表现或工作安排表达。技术评审保留理解方案所需的原因、接口和异常影响。既定分工、已确认方向和未决口径各按材料状态写，不为简洁删掉，也不改成审批表。

材料筛选示例：素材包含“计划周五发布、上线日期不能由测试通过推定、窗口待双方对齐”。汇报安排写“计划周五发布，双方先对齐发布窗口，确认后同步安排。”保留计划与前置事项；核稿时用的推定说明不另附一句。

功能说明也按这一办法写：预计与实际数据分别展示、待补金额留空、已有轨迹可看，就分别写明这些页面行为。涉及统计时明确纳入哪些日期；涉及评审时保留会影响方案判断的机制和异常。功能已经说清时，不追加一串“并不代表……”来重复同一事实。
