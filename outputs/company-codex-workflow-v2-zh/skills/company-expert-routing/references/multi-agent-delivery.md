# 多 Agent 交付操作说明

这是 [company-agent-routing](../../company-agent-routing/SKILL.md) 使用的操作说明。复用原生代理、已有角色和阶段技能，不新建调度器、后台守护或运行器。DELEGATE-01、REVIEW-01 及既有 AUTH、FLOW、REPAIR、EVIDENCE 规则保持适用；角色分工不替代质量验收。

启用条件和用户告知由独立入口负责。普通工作流仍可单独使用；help 仅作兼容转交，不是必经步骤。用户不填写内部任务包。

## 1. 确定任务与当前能力

复用真实用户请求与已确认规格中的目标、范围、验收、终点及授权来源。“用多agent完成某任务及独立审查”已表达本任务派发意图，无须特殊口令或重复审批；这句话本身不授权尚未确认的业务实现、提交、推送、合入、部署、生产操作或外部发消息。连续完成所有已授权工作，只问确实缺失的决定或权限。

检查当前宿主工具说明中的派发、通信、等待、中断、结果查看、命令及会话控制能力，记录可用与缺失项。工具名和参数可能跨宿主不同，按当前 schema 调用，不复制假定的 API。Agent TOML 经核实可作为角色文本来源，但存在文件不证明自动加载。每次原生派发显式携带角色正文和任务包，记录真实返回的 agent ID 和调用证据，不能只写一个计划角色名。不用新建用户聊天代替子代理，也不自动安装或配置代理。

缺少原生派发能力时，主代理串行完成允许的工作，记录 `single-executor fallback`；自查不能冒称独立审查。独立审查属于验收必要条件时，该项仍未满足，其他授权工作继续。缺少运行控制能力会限制长命令派发；优先有界检查并说明限制。

## 1a. 从业务资料贯穿到交付

用户可以只提供业务资料或想法并要求多 Agent 连续交付，不必先写规格、拆任务或指定技能。主代理先读取已授权材料和已有产物，定位最早缺失的阶段，再按下表推进。表中阶段只是工作说明，不是新增状态枚举；业务理解沿用现有需求/上下文工作，按需交接不另建状态。已完成且仍适用的阶段不重做；同一执行者可以连续承担阶段，不强制每阶段新建代理。

| 阶段 | 现有工作流技能 | 按需专家 | 传给下一步的可检查产物 |
| --- | --- | --- | --- |
| 业务理解 | [company-context-index](../../company-context-index/SKILL.md) | [business-analyst](../../business-analyst/SKILL.md)：流程、指标或来源冲突 | 原材料路径/版本/位置、事实与推断、冲突及未决决定；原始业务意图 |
| 需求 | [company-feature-requirements](../../company-feature-requirements/SKILL.md) | [product-manager](../../product-manager/SKILL.md)：范围及验收；业务口径仍按需用 business-analyst | 稳定需求ID、来源原义、范围/排除、AC与异常反例、仍缺的决定 |
| 设计 | [company-feature-design](../../company-feature-design/SKILL.md) | 按当前技术栈和风险用本路由的专家映射 | 需求ID→方案/契约/数据流/风险/测试策略，未决实质取舍 |
| 任务 | [company-feature-planning](../../company-feature-planning/SKILL.md) | 仅对未解决的技术或验证问题选专家 | 需求/AC→任务ID、允许文件、依赖、验证点与反例 |
| 实现 | [company-implementation-runner](../../company-implementation-runner/SKILL.md) 或缺陷路径 [company-bugfix-runner](../../company-bugfix-runner/SKILL.md) | 当前技术栈专家；测试设计有难点时补 testing-qa | 任务/需求ID→实际变更、测试与原始输出，未完成项 |
| 质量验收 | [company-quality-validation](../../company-quality-validation/SKILL.md)，沿用既有触发条件 | [testing-qa](../../testing-qa/SKILL.md)：独立预期、回归与反例 | 最终候选上逐需求/AC的通过、失败、未验证证据及影响 |
| 收口 | [company-delivery-closeout](../../company-delivery-closeout/SKILL.md) | 仅在剩余风险需要时补专家 | 授权终点及实际成果、验收证据、残留事项、交付限制 |
| 按需交接 | [company-thread-handoff](../../company-thread-handoff/SKILL.md) | 通常无需新增专家 | 原目标/需求ID与原义、决策及理由、候选、有效证据、未决项、授权和下一动作 |

阶段入口必须实际读取并应用；专家只对当前具体问题按需加载，不全量读表中技能。派发者先把链接解析成当前已核实的准确路径；只交付角色名、技能名或表格不算调用。已确认需求起步时从设计补最早缺失项；已有有效设计/任务起步时进入实现。只聊想法且未要求成稿时不落正式文档；明确要求讨论稿或评审文档时按文档授权完成，不因此进入实现；仅需求授权完成需求后停止。整体授权覆盖后续且前置条件满足时，按 FLOW-01/02 连续推进，不增加阶段口令。新业务规则、冲突材料无法确定的口径或实质新架构取舍，仍只向用户询问缺失决定；已有材料中的答案先读取，不反复提问。

### 技能读取与应用证据

在第3节既有 `inputs` 中列出：本阶段必须读取的技能准确路径与相关章节（需全文时明确全文）、共享约束适用章节、业务原材料及上游产物的路径/版本/位置、需求ID/AC、未决项与对本阶段的影响。派发时范围必须允许读取这些来源；不能只写“按最佳实践”，也不能让代理在范围外自行找技能。当前主代理已读过不代表子代理已读过；同一代理已读且内容未变可引用其真实读取证据，不重复读。

在第4节既有结果和执行记录中返回：实际读取路径、内容 SHA-256、读取章节、对应工具轨迹或原始命令输出位置；采用的具体规则→产物路径/章节或行号；未采用的相关规则及理由、无法读取/未执行的项。主代理结合当前工具轨迹或可回查的原始输出、文件指纹和产物逐项核对。仅自报读过、hash清单或角色名称均不证明技能已应用；hash只能标识内容，不能证明阅读或执行正确。轨迹不可见或输出不完整时保留限制，补核受影响项；不得把缺失证据标为通过。

技能不可调用时区分“实际读取并采用内置文件规则”和“仅采用专家视角”；两者均不冒称原生技能调用。可替代的辅助视角缺失时说明降级；不可替代技能、必要审查或其必要证据缺失时，对应要求仍未满足，继续不依赖它的已授权工作，不宣布阶段或整体通过。不改 `task_state` schema，不新加派发表字段。

### 按原义交接和独立判断

每个交接沿用同一需求ID，关联“原材料位置与原义 → 需求/AC → 设计 → 任务 → 实现/测试 → 质量证据 → 收口或交接”。接收者核对上游版本、继承范围、反例、未决项及授权；不能把作者的概括替代原材料，不能因换阶段丢失排除项或把未决推断写成确认事实。来源冲突保留各自出处、时间和适用范围；只有证据支持时才能判定替代关系，不能仅凭较新日期覆盖仍适用的规则。

审查对象随阶段变化：业务/需求审查以原材料、含义、范围、AC和异常为依据；设计/任务复核查需求覆盖、契约、依赖和可验证性；实现后审查与质量验收再查实际代码/测试/运行输出。需要审查时固定该次相关文档/材料或代码候选指纹，不把代码 diff 或同一冻结代码流程强加给所有阶段，也不强制每阶段单独开审查代理。

需求层审查按 [原始材料独立覆盖审查](../../company-feature-requirements/SKILL.md#原始材料独立覆盖审查)：先只读原始材料提炼必须保留的业务关系、关键属性和核心用户操作，保存独立覆盖依据及顺序证据后再读取作者需求和 AC；逐项映射到需求/AC、缺项、待确认或有来源/授权与可解释边界的暂缓。检查作者 AC 全过但原要求仍遗漏的反例，无依据的省略或收窄不得通过。未知事实继续待确认，不强加业务规则或生产算法；已有作者内容污染时如实标明独立性限制，不倒填记录或自行加轮次。质量验收必须回查这份依据与原材料，不能只信作者 AC。随后检查事实/推断混用、遗漏来源冲突、缺失当0、异常数据静默当正常、范围或分母含义漂移。存在业务歧义时列可回查的不同解释，不自选一个答案。质量验收继承这些反例并按原始规则独立推导预期，再核对实际输出；通过作者测试或多代理投票不能替代独立判断。问题返回原需求ID、来源位置、冲突含义、反例及影响，沿第4节有界纠错；任何改变原业务规则的修正须有真实决定来源。

### 人类交付的整合与审查

面向人阅读、讲解或操作的结果，按 [表达规范](../../../specs/global/assets/human-output-standard.md) 的“交付阅读检查”执行。既有 inputs 和 acceptance 同时给执行者与审查者写清受众、用途、现有基础、本次变化和读者入口。执行者按文档写作技能交稿；主代理统一业务主线，不拼接各代理报告。沿用当前独立审查增加具体复述和歧义定位，之后对照来源修正；不新增字段、角色或审查轮次，不把源材料优先的原义审查冒称无背景读者测试。

## 2. 最小角色与顺序

| 角色 | 职责 | 边界 |
| --- | --- | --- |
| 主代理 | 授权、共享契约、任务状态、分派、集成、证据核对和最终结论 | 共享状态和验收结论单写；子代理输出只作为待核对证据 |
| 执行者 | 完成当前阶段的窄任务产物及验证，返回变更路径和原始证据 | 不改共享状态和验收标准，不超任务包执行 Git 交付或外部操作 |
| 独立审查者 | 对当前阶段固定候选核对原材料、验收及适用的 diff/证据，运行允许的聚焦检查并返回问题 | 与执行者是不同代理；默认只读、不直接修实现；独立审查不自动等于盲审 |
| 按需探索员 | 对具体未知事实调查并返回证据或选项 | 只读，不决定未确认的业务规则或架构，不获得实现授权；证据已足够则省略 |

需要独立审查时采用执行者 → 当前阶段候选 → 审查者 → 主代理验收；阶段判断见第1a节。主代理也可以亲自执行，再交独立代理审查。不为了凑角色增加代理；仅实际要求盲审时应用 REVIEW-01。

并行要求输入独立、写路径互斥、不依赖未完成结果，并满足 DELEGATE-01 的收益证据要求。没有可比实测时保持角色串行交接，不声称提速。禁止并行修改同一文件、共享契约/状态、迁移或公共文档段落；审查仍在变化的候选不能作为验收，先冻结或结束相关修改。只读探索也仅在满足上述条件时与独立工作并行。可用槽位是上限，不是必须填满的目标。

## 2a. 多项目的最小协调

只协调用户本次已授权的项目，不从任务名或工具可见性推导其他项目权限。每个项目保留自身负责人、权威任务状态和证据；协调者只读简短状态摘要、依赖和待决，具体执行者接收本项目的窄材料，不建立包含所有项目正文的巨型上下文。

在现有执行记录中维护下列摘要即可，不新建调度服务或给 task_state 添加字段：

| 项目/任务及状态引用 | 负责人/唯一写入者 | 优先级及依据 | 前置依赖/恢复条件 | 独占资源及当前持有人 | 当前结果/证据 | 下一已授权动作/真正待决 |
| --- | --- | --- | --- | --- | --- | --- |

一次只给一个任务一个权威状态写入者。派发前明确本轮并发上限，优先遵守用户约束及当前宿主容量；没有可比收益证据时仍可串行推进，不能为占满槽位而派发。先选前置条件满足且资源空闲的最高优先任务；同优先级沿已有任务顺序，不自行引入新的业务优先规则。低优先任务的独立已授权工作可以在高优先任务等待时继续，记录选择原因。

资源包括写路径、共享状态、端口、服务、浏览器会话以及会产生同一外部副作用的动作。取得资源前核对实际归属；同一资源只有一个持有人，不依赖“代理完成”字样释放。中断/取消后按第5节核对真实停止，停止未知则保留占用并阻塞相关任务；继续无冲突任务。负责人变更须先确认旧执行者及其归属工作实际停止，核对已有结果，再登记交接，禁止双写和重复操作。

项目内事实由其负责人负责核验，协调者核对摘要对应的候选、状态revision和证据引用；过期摘要只触发相关事实查询，不重跑全部项目。某项目缺业务决定时只列一个明确待决项及影响，不能将其当所有项目的停止条件。总汇报聚合成果、关键选择/理由、证据、下一动作与真正待决，不替代项目验收。

争议先统一为原要求/AC、固定候选、可复现反例、原始输出与影响的单份反馈，按第4节定点纠错；协调者依据复验结果裁决，不以角色数量投票。没有新证据或达到修复上限时，停止争论并保留该项未通过，继续独立任务，不降级验收。

## 3. 可直接派发的窄任务包

复制下表文本，从真实来源填写，再附上对应角色正文。未知预算保持未知，不编造时间或 token 限制。这是派发记录，不是新状态 schema；不得自动给现有契约增加字段或状态值。

```text
task_id: <既有任务ID及局部指派>
role: <executor | independent reviewer | explorer>
authority_source: <可回查的用户请求/已批准记录及范围>
goal_and_endpoint: <具体产物与已授权终点>
acceptance: <AC编号、准确预期和失败案例>
candidate_fingerprint: <真实revision及脏文件/内容hash，来源路径>
inputs: <第1a节的阶段技能准确路径/章节、业务源材料、上游产物、需求ID/AC、未决项及原始证据>
allowed_paths: <完整允许读写路径，区分只读>
forbidden_actions: <排除路径、共享状态、Git与外部操作>
immutable_contract: <固定字段准确名称、类型、值及封闭状态集合>
editable_contract: <仅允许改的字段、正文部分与文件范围>
verification: <命令/检查、cwd、所需观察与原始日志位置>
budget: <已约定时间/token/尝试次数，未知则unknown>
output_location: <默认agent回复；获授权时使用明确文件路径>
runtime_ownership: <如何登记真实会话/进程身份及停止机制>
stop_conditions: <取消、到限、范围冲突、依赖不可用>
result_format: <使用第4节；未知如实报告>
```

执行者正文：“读取 inputs 中的阶段技能及来源，按本阶段交付产物并返回规则应用证据；只执行本任务包，准确保留不可变字段。编辑前检查候选与范围。不改验收或共享状态。执行指定验证并保留真实输出。宿主允许时登记真实长命令/服务身份后继续。遇到冲突或取消停止受影响工作，保存产物并报告真实运行状态。按结果格式返回，不自行宣布整个任务完成。”

审查者正文：“读取 inputs 中的阶段技能及原材料，按第1a节独立形成预期和反例，核对本阶段候选、验收与固定字段。检查适用于本阶段的产物、真实 diff 和原始证据，不依赖执行者结论。不改实现或共享状态；只运行获准聚焦检查。问题写明路径/位置、具体失败案例、影响和所需纠正；无问题也说明覆盖与限制。返回前再次核对候选身份。未满足 REVIEW-01 不称盲审。”

探索员正文：“读取 inputs 中的适用技能与来源，返回采用规则及证据；仅用范围内证据回答指定未知问题。不改文件、不决定未确认业务规则。返回来源、观察事实、未知项及对当前任务的影响，不扩展任务。”

## 4. 结果格式与一次局部纠错

以下格式仅用于代理回传与内部记录，不直接粘贴到用户回复或成稿。返回第1a节的技能读取/应用证据与需求原义追踪，以及真实 `task_id`、`result_id`、agent ID、角色、输入和输出 `candidate_fingerprint`、读写路径、AC映射、固定字段核对、原始验证证据、问题、未知项、剩余运行身份和下一动作。每项检查保留命令、cwd、实际起止、退出码、原始 stdout/stderr 或可回查位置；有数据才记录实际耗时和预算消耗，不编造 token 用量。DONE 等回复标记不是证据，也不是新增持久化状态值。

原始记录须绑定被测命令实际执行的 argv 与 cwd，不从外层采集命令推断；涉及编码等样本属性时，在既有执行前核对实际输入字节符合所测属性。采集修正只重验受影响用例，按轮保留并区分原始结果，不覆盖旧轮记录；候选与适用条件未变的有效证据继续复用。

主代理按第1a节核对技能使用和需求追踪，再核对身份、范围、固定字段、原始结果和候选新鲜度。重复 result_id 不重复集成；冲突结果都保留，只调查争议事实。越界改动先隔离核对，不覆盖用户文件、不静默采用。

普通范围内缺陷合成一份反馈包交执行者，包含具体问题、原 AC、不变的固定字段、允许纠错范围与复验命令。允许一次局部纠错；按新指纹复核修改部分并重跑受影响检查，不重开整个任务，不为过评分而改固定字段。仍失败则停止重派循环，按现有修复策略有界串行接管。主代理修复会使受影响的审查证据失效；独立审查必要时，须在已有限制内由另一代理复核最终候选，否则明确该项未满足。缺业务决定或新增范围交用户，独立工作继续。一次纠错不授权无限重试。

## 5. 长命令、取消与恢复

委派长命令/服务前安排记录真实工具会话ID，以及能力允许时的进程ID、启动时间、命令、cwd和本任务归属；返回身份后立即登记。PID可能复用，不能只凭数字或旧日志推定归属。使用当前宿主机制与既有任务记录，不新建后台控制器。无法建立身份或控制时，不启动不能安全管理的无人值守工作；在范围内采用有界替代，或保留该检查待办。

取消或到限时，主代理停止新派发和依赖动作，要求本任务实际代理停止，再通过原生能力检查已知归属会话/服务。保留有效产物和原始结果。代理标记 interrupted、cancelled 或 completed 不代表其 shell 命令、子进程或服务已停止。核对当前会话终止/退出结果，适用时确认对应归属进程或服务已不存在。停止证据缺失或矛盾时在执行记录写明 `stop unverified`：禁止重派该工作或释放其依赖资源/动作，仅继续独立工作。不杀无归属或范围外PID，不按宽泛进程名批量终止，不导入实验 `stop_gate` 脚本当通用杀进程工具，不用历史日志作为当前停止证据。停止需要额外权限时，报告准确运行身份和所需动作。

恢复先核对最新用户意图、授权、候选指纹、真实代理/会话/进程、既有结果及任务状态，再行动。取消在用户真实恢复前持续有效，旧记录不能重新激活任务。未知副作用先调查，不重放。停止已证实且恢复有授权后，只选择受影响未完成项；复用有效证据，对漂移补验。保留旧ID与证据，登记新指派身份。失败或不可访问的检查保持未验证，不能算通过。

## 6. 验收、收口与计量

主代理把每项AC映射到最终候选证据，核对固定字段与允许变更路径，确认必需独立审查，并按既有规则决定 `company-quality-validation`。审查问题清单不等于集成验收，本地测试不等于真实API或生产证据。解决或明确报告剩余失败和运行中任务；缺必要证据阻塞对应验收。

从当前最早缺失的业务/需求/设计/任务阶段沿对应工作流，经过实现/bugfix、必要验收和 `company-delivery-closeout` 连续做到已有授权的 prepare/commit/deliver 终点。只通过现有状态工具支持的schema和revision协议更新，主代理单写；不手改状态、不扩展状态值、不自动提交推送，也不把角色分工当外部业务操作许可。不新增审批门禁。

在既有执行记录保留真实起止和墙钟耗时；各角色执行、协调/等待、纠错耗时；用户介入次数与原因；AC通过/失败/未验证数；重跑、候选ID变更与能力限制。区分缺失决定和可避免的重复审批，不把重叠角色耗时相加冒充墙钟耗时，未知计量保持未知。只有验收、范围、环境、证据完整性可比，且包含协调与重跑成本时，才声称提速；单例不证明普遍性能收益。

给用户说明交付结果、达到的授权终点、实际角色调用或回退、验证/审查覆盖、剩余限制及一个下一步。实现、审查、验收、提交、推送和部署分开陈述；还有已授权可执行工作时，不停在建议下一阶段。
