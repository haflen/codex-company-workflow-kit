# 公司多 Agent 入口

用户只需选择本技能并说明任务、交付用途和材料。你负责判断当前阶段、安排必要角色、调用现有工作流能力并推进到约定终点；不让用户选角色、填任务包或逐步回复“继续”。

## 启用与告知

用户选择本技能来执行具体任务，或明确要求“用多 agent”，就是该任务的派发许可，不再询问是否启用。只引用本技能讨论、评估或修改它，不是派发业务代理的许可。普通工作流和单执行者仍独立可用；最新“不用 agent”优先，按已有取消规则确认实际停止并保留成果。

先用一两句告诉用户：本次做到什么、哪些角色将负责什么、使用哪些业务能力。实际调用返回后才说“已派发”；分工变化或能力受限时更新。结束说明实际参与和发现的问题，不把内部任务包当作交付。

## 自动安排工作

1. 读取项目上下文和当前任务资料，先核对已有能力及用户要改的地方；有现成成果就接着做。旧系统改造须分清已有可复用、需要调整、确实新增及尚未核实，不把完整业务流程全部列为待新建。仅在明确新项目或独立重做约定下从零开始；隔离重做不得借此读取禁止材料。
2. 按 [多 Agent 操作说明](../company-expert-routing/references/multi-agent-delivery.md) 第1a节，从最早缺失阶段使用现有工作流。需要专家选择时用 [专家路由](../company-expert-routing/SKILL.md)，不回到 help 重新选择模式。先整理完整任务顺序，之后连续执行已授权工作。
3. 采用说明中的最小角色：主代理统筹与集成，执行者完成工作，另一名代理独立审查；确有未知问题再安排探索员。同一执行者可覆盖多个阶段。并发收益不明确时串行交接，不为了角色齐全增加代理或审查轮次。任务包沿用已有字段，写清来源、允许修改范围和不可变约束。
4. 通过真实工具派发、收回并核对产物和原始证据；共享状态单写，失败局部修复。取消后确认实际进程停止才重派。无原生能力时说明由单执行者处理，必要独立审查仍记为未满足，不假扮多个角色。

## 面向人的交付

先读 [表达规范](../../specs/global/assets/human-output-standard.md)。交付汇报、产品方案、操作说明或原型时，同时使用 [文档写作](../company-document-writing/SKILL.md)。把读者、用途、现有基础、本次变化、材料入口和必要术语解释放进既有 inputs 与 acceptance，执行者和审查者都收到；不只让协调者知道。

主代理按同一条业务主线整合各角色产物，不拼接代理报告。既有独立审查中加入“仅凭成稿能否理解”的检查：审查者先看读者会拿到的正文、图和页面，复述本次改动、使用过程、依赖和需要人处理的事项，再对照来源检查误解、遗漏或越界承诺。与来源优先的原义审查区分记录，不混称盲审。具体方式见表达规范的“交付阅读检查”；不新增专职写作代理或审批关卡。

## 连续执行与边界

按 [任务执行约定](../../specs/global/assets/task-execution-policy.md) 的 READ-01、AUTH、FLOW、REPAIR、EVIDENCE 及适用 WAIT-01 继续到用户约定终点。普通可逆选择自行推荐并执行，真实缺失业务决定或权限只阻塞相关动作。多 agent 不自动授权业务实现、Git、部署、外部消息、自动化或创建新聊天。

用户明确要求离开后继续时，核对可用的续做机制、有效授权和本地运行前提，成功建立后才承诺跨轮继续。任务状态文件本身不会唤醒任务，不能承诺关机或合盖后仍执行。沿用现有工具与规则，不另建调度系统。

### 回复契约门禁

交付前按上述表达规范核对当前结果、事实依据、读者理解和实际显示；有已授权工作就继续，缺决定只问具体缺项，不把内部派发记录贴给用户。
