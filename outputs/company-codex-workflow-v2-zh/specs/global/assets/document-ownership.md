# 文档归属与记录粒度

文档位置由业务归属决定，记录详略由行为变化和风险决定；交付批次不改变功能归属。本规则与 document-standard.md 配合，不新增技能或审批阶段。

## 写入前：只核对当前任务

1. 读取 INDEX 的文档职责地图、当前任务及其直接关联的模块/版本入口，不全仓扫描。
2. 优先复用已有 work-item-id 和权威记录。确认 owner-path（归属目录）、record-path（本次记录）、release-target（交付批次，可为未定）。将这些信息写入已有内部任务或执行记录的元信息，不为检查单独建文件；未开始写文档时只需在上下文中保留。
3. 项目已有版本/里程碑目录时，继承当前功能归属；不能因为变更小、分支新或修改日期晚，就新建根级 specs/features/。项目明确采用 feature 布局时保留其约定，不强迫改成 versions。新项目尚无约定时先确认一次布局。
4. 共享认证、构建和治理使用项目已有公共归属；没有归属或多个候选冲突时，仅询问归属，不猜最新版本。归属未确认前不新建永久文档包；可继续只读分析。
5. 后续阶段继承已确认归属；只有业务范围或归属证据改变时才重新判定。归属检查不授予编码、移动文件、提交或发布权限。

## 自动选择记录粒度

| 情况 | 记录方式 |
| --- | --- |
| 当前任务未验收，修复遗漏或实现错误 | 续写原任务及验证记录，不另建 bugfix 文档包 |
| 已有功能的低风险修复，未改变已确认业务承诺 | 复用所属模块已有修复日志，增加有稳定编号的条目；没有日志时创建一份紧凑修复记录 |
| 少量代码但涉及权限、金额/公式、数据迁移、跨系统或其他高风险 | 同一归属下补必要专项方案、回滚与验证证据，不以行数降低验证等级 |
| 新能力或改变已确认业务规则 | 进入需求/设计变更流程，按影响更新权威文档并确认后执行 |
| 多版本共用的修复 | 一个权威记录，各受影响版本和发布清单引用，不复制多份正文 |

内部紧凑记录包含：work-item-id、owner-path、record-path、release-target、问题与预期、修复范围、验证证据/未验证项、当前状态及下一步。已有模板字段可复用，不重复堆叠。不强制补齐需求/设计/任务三件套。正式需求、设计及正式修复记录仍遵守 document-standard.md 的对应图表要求，轻量不等于自动豁免图表或真实 API 验收。

记录类型判定：在现有任务/修复日志中追加条目，只检查本次影响的追溯、图文一致性、验证和漂移，不把整份历史日志重新套模板；新建独立正式修复报告时，补结论及“问题→原因→修复→验证”Mermaid 图。已受影响的原需求/技术图仍须同步更新，不能用紧凑条目替代；未影响的图不重复绘制。

人类文档只保留读者需要的任务编号、范围、结果及证据链接；不复制内部归属字段清单。具体表达遵守 human-output-standard.md。

## 收口与历史记录

- 分开记录实现、验证、提交、合并和部署状态；只更新有证据变化的字段，不从 Git 提交推断已上线。
- 已验收/已发布基线不静默改写；修复记录引用原基线并说明变化，当前权威规格需要更正时显式记录对比基线。
- 日期化的历史结论保留。承担当前状态的 README/任务入口必须更新，并链接最新证据，避免“尚未提交”继续冒充当前事实。
- INDEX、项目说明和版本 README 只在阅读路径、范围、阶段或发布状态改变时更新；遵守公共文档分支协议，业务分支使用 public-doc patch，不把局部进度直接升格为主线状态。
- 健康检查只报告错放、重复权威正文、断链和陈旧当前状态；迁移须先给出旧路径→新路径及引用影响清单，经用户授权再移动。不自动重排编号、删除历史记录或覆盖业务内容。
- 资产路径检查通过不等于文档归属正确。本规则是工作流语义检查，不宣称已有脚本自动验证业务归属。

## 验收场景

| 场景 | 必须得到的结果 |
| --- | --- |
| OWN-01 已有版本下的小图例修复 | 留在原模块；紧凑记录；不创建根级 features |
| OWN-02 未验收任务中发现遗漏 | 续写原任务；不创建平行需求包 |
| OWN-03 两行金额公式修复 | 原归属不变；高风险验证不降级 |
| OWN-04 多版本共享登录修复 | 单一公共权威记录；版本引用，不复制 |
| OWN-05 老功能随后续版本发布 | owner-path 不随 release-target 改写；发布清单链接修复 |
| OWN-06 未知归属或历史目录混用 | 保留现状并询问关键归属；不自动搬迁，不全仓重写 |
