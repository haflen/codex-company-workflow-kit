# 公司正式文档阅读与图表标准

## 适用范围

本标准适用于新建或发生实质更新的需求、业务规则、技术设计、数据模型、API 契约、任务计划、Spike、Hotfix、需求原型记录、交付收口、项目上下文索引、验收报告、操作指南和管理汇报。历史文档不自动重写。

先按 human-output-standard.md 确认读者和用途。内部执行信息另存，工程评审所需的编号、字段、公式和图表保留。

## 按读者组织内容

标题可改名，章节可合并或调整顺序；模板展示参考骨架，成稿按内容完整性检查，不按标题字面匹配。开头必须说明结论与影响，正文保留适用的依据、风险和下一步责任。以下是建议阅读顺序，仅保留适用内容；用户明确指定结构时沿用其要求。

1. 先看结论。
2. 本次变化。
3. 建议阅读路径和图例。
4. 核心 Mermaid 图。
5. 场景、流程和逻辑解释。
6. 详细规格。
7. 异常、风险和验证。
8. 评审结论和下一步。

## 元信息与追溯编号

工程规格中的每个 feature 或 milestone 定义稳定的 `work-item-id`。验收报告保留关联任务与候选版本；操作指南、管理汇报按需引用已有任务、版本或来源，不为套模板新造编号。跨文档引用使用 `<work-item-id>/<本地编号>`。

| 对象 | 本地编号 | 完整引用示例 |
| --- | --- | --- |
| 流程节点 | `F-nnn` | `STP-M1/F-001` |
| 业务规则 | `BR-nnn` | `STP-M1/BR-001` |
| 验收标准 | `AC-nnn` | `STP-M1/AC-001` |
| 设计决策 | `D-nnn` | `STP-M1/D-001` |
| API 契约 | `API-nnn` | `STP-M1/API-001` |
| 实现任务 | `T-nnn` | `STP-M1/T-001` |
| 测试或验证 | `TC-nnn` | `STP-M1/TC-001` |

编号发布后不得因排序变化而重排；废弃对象保留编号并标记状态。跨文档引用还必须提供文档路径或章节链接。

## 本次变化

版本变更评审必须说明相对上一确认版本的变化、原因、影响及可核对基线；多项变化用表格，单项可用段落。基线引用适用的版本、来源路径或 Git commit，未知时说明缺口。初稿不要求变更表；操作指南和管理汇报只有承担版本比较用途时才加入变化对比。模板中的“本次变化”是参考栏目，不固定位置。

| 变更项 | 上一版 | 本版 | 变更原因 | 影响范围 |
| --- | --- | --- | --- | --- |

## Mermaid 规范

- 图前写明要回答的问题，图后解释读者需要的关键结论，不为固定条数填充内容。
- 节点优先使用中文业务名称，代码名放在第二行或括号中。
- 一张图只回答一个主要问题；超过约 20 个节点时拆成总图和局部图。
- 不依赖颜色表达唯一语义，使用线型、标签和文字共同说明。
- 按下表判定图表要求。文档同时承担多种用途时，分别保留对应要求；管理汇报不能替代技术设计，也不能通过改名规避技术图表或必要证据。
- 无法完成渲染检查时必须标记“Mermaid 渲染：未验证”，不能描述为已通过。

## 按文种选择图表

| 文种或用途 | 图表与内容要求 |
| --- | --- |
| 需求、业务规则 | 保留对应业务流程图与关键判断 |
| 技术设计 | 保留总体架构图与 `sequenceDiagram`；两者分别检查 |
| 数据模型、API 契约 | 数据模型保留关系图与数据形成时序；API 契约保留交互时序 |
| 任务、原型、Spike、Hotfix、交付收口、项目索引 | 沿用对应模板已规定的依赖、业务流程、实验、修复、成果关系或阅读路由图，不把所有模板的图叠加到同一文档 |
| 验收报告 | 保留范围、候选、结果、证据及未验证影响；跨阶段验收、交付与上线观察的关系用流程图说明，单项结果核对可用证据表 |
| 操作指南 | 顺序操作使用步骤与判断表，保留位置、命令、预期、停止条件和恢复；存在跨角色交接或循环恢复路径时补流程图 |
| 管理汇报 | 架构分工用分工图，阶段交付用推进图；只汇报状态、风险或决策时可用段落与表格，不强制工程时序图 |

不适用不是图表豁免：先依据文种和实际内容确定要求。已确认必需的图和用户明确要求的图不能按篇幅自行删除；对适用图的豁免仍按下节办理。

## 图表豁免

只有用户明确说明不需要某张图时才允许豁免。豁免记录必须包含用户、图表对象和原因。AI 不得因任务简单、时间紧或技术路径唯一自行豁免。

## 复杂度与篇幅

- L1 可以合并相邻章节，但结论、对应图、关键规则、验证和下一步不能省略。
- L2 覆盖该文种适用的完整内容，标题与顺序可按读者调整。
- L3 在完整结构上深入说明跨域关系、迁移、并发、恢复、版本和一致性。

复杂度只决定展开深度，不改变图表和证据要求。

## 文档质量门禁

| 门禁 ID | 检查项 | 通过标准 |
| --- | --- | --- |
| `DOC-G01` | 结论内容 | 开头明确问题、结论与影响；正文提供依据、未完成项和下一步责任，存在待决事项时说明；不限定标题 |
| `DOC-G02` | 需求图表 | 存在目标业务流程 Mermaid 图，或有用户明确豁免 |
| `DOC-G03` | 技术图表 | 分别存在总体架构图和 `sequenceDiagram`，或有对应豁免 |
| `DOC-G04` | 类型化图表 | 按文种和实际内容包含适用图；适用图未提供须有用户明确豁免，不以改名规避要求 |
| `DOC-G05` | 豁免 | 记录用户、对象和原因；AI 自行判断无效 |
| `DOC-G06` | 图文一致 | 图中节点、状态、表和接口均有正文解释 |
| `DOC-G07` | 主链与异常 | 正常路径和关键异常均有明确行为 |
| `DOC-G08` | 追溯格式 | 本地编号格式正确；跨文档引用包含 `work-item-id` |
| `DOC-G09` | 追溯完整 | 流程、规则、AC、设计、任务和测试可以互相定位 |
| `DOC-G10` | 可见结果 | 技术结构能追踪到页面、接口或业务结果 |
| `DOC-G11` | 渲染 | Mermaid 已渲染检查；否则明确标记未验证 |
| `DOC-G12` | 漂移 | 文档、脚本、代码和实际路径没有明显冲突 |

图表类门禁仅在对应文种和内容适用时检查；无图且不要求图时 DOC-G11 不适用，仍按 human-output-standard.md 检查正文显示。追溯类门禁按工程规格、验收关联或来源引用检查，不要求管理稿补齐工程编号矩阵。结构检查不能代替证据内容审阅。

## Workflow 责任

- `company-feature-requirements`：`DOC-G01`、`DOC-G02`、`DOC-G05` 至 `DOC-G12`；生成业务规则时加 `DOC-G04`。
- `company-feature-design`：`DOC-G01`、`DOC-G03`、`DOC-G05` 至 `DOC-G12`；涉及数据模型或独立 API 契约时加 `DOC-G04`。
- 规划、原型、Spike、上下文索引和交付收口：`DOC-G01`、`DOC-G04` 至 `DOC-G12`。
- Bugfix 默认在受影响范围检查 `DOC-G06` 至 `DOC-G12`；新建独立正式 Bugfix/Hotfix 报告时增加 `DOC-G01`、`DOC-G04`、`DOC-G05`，包含“问题→原因→修复→验证”Mermaid 图。续写任务/修复日志不触发整份历史文档重写，具体粒度见 document-ownership.md。
- 实现只检查本轮更新的权威文档：`DOC-G06` 至 `DOC-G12`。
- 健康检查诊断 `DOC-G01` 至 `DOC-G12`，默认只报告，不自动重写。

## 人工阅读检查

结构门禁不能代替人工判断。阶段结束前仍需确认：业务、产品、开发和测试是否能从结论、图表、正文和追溯关系得到同一套理解。
