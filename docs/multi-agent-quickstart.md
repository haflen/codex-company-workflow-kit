# 工作流与多 Agent：怎么使用

**想用工作流就说“用工作流帮我……”；想让多个代理协作就说“用多agent帮我……”。** 不需要选择技能、指定角色或先替我拆任务。多 Agent 复用同一套工作流能力，只改变谁来执行和独立检查。


## 直接选择多 Agent 入口

选择 `$company-codex-workflow-v2-zh:company-agent-routing`，贴上材料和目标即可，不必先调用 help：

```text
用多 agent 完成下面的任务：先核对项目已有能力，再按业务材料推进到约定交付；你安排分工、调用工作流技能并做独立交叉审查。过程告诉我谁在做什么，交付用我和同事能看懂的说法。普通步骤连续完成，只在缺少关键业务决定或权限时问我。

任务目标和材料：……
```

普通工作流仍可独立使用；`company-expert-routing` 负责挑选专家能力，`company-agent-routing` 负责组织代理协作。明确选择多 Agent 后不再逐次确认启用。这个选择本身不授权提交、推送或部署；离开后跨轮继续仍需实际建立可用的续做机制。


## 一段可直接复制的启动提示词

在目标项目新开聊天，复制下面整段并替换业务材料占位内容即可：

```text
使用公司工作流的多 agent 模式，从下面的业务材料开始，连续完成需求梳理、方案、实现、测试和独立交叉审查，直到交付可验收成果。常规决策按推荐方案执行，不要逐步找我确认；只有缺少关键业务事实或超出授权时才问我，其余工作继续。审查者先独立阅读原始材料，再核对执行成果；发现问题后据证修正并复验。开始时简短告知参与的 agent 和技能，过程中告知关键决定、进展与阻塞，最后统一交付成果和验证证据。我离开后继续已授权工作，请实际建立并确认可用的跨回合续做机制；无法建立时明确告知。允许修改本项目、测试和打包，不提交、不推送、不部署。

业务材料：
【在这里粘贴材料】
```

离开后续做需要电脑保持唤醒、Codex 可用；助手应实际确认续做机制，不能仅凭提示词承诺后台执行。

## 两种方式

| 你怎么说 | 我怎么做 | 开始时会告诉你 |
| --- | --- | --- |
| “用工作流帮我梳理这些业务材料。” | 当前代理按现有流程完成，按需使用业务、需求等技能，不另派代理 | “本次按普通工作流，由我使用业务分析和需求梳理能力，整理业务规则与验收标准。” |
| “用多agent完成这个需求，做独立审查。” | 主代理安排执行者、独立审查者，必要时增加探索员，汇总交付 | “本次用多agent协作：执行者完成需求梳理，审查者核对业务原义；我负责协调和交付。” |

首次提出多agent请求本身就是选择，不会再追问“是否启用”。同一任务已授权时，后续按需调度并告知实质变化；不会每派一个代理都请求确认。没表达多agent意愿时正常走工作流，不在开头强迫你二选一。只是讨论agent或说“独立检查”，不当成另派代理的许可。

普通工作流照常保留测试和质量验收；如果具体约定确实要求另一位执行者独立审查，而尚无派发授权，会说明这一缺口并询问一次，不用自查冒充通过，也不反复推荐多agent。

## 从任何进度开始

- 只有想法或业务材料：“用工作流帮我梳理这个业务，先形成需求文档。”
- 需求已明确：“用工作流按这份需求完成设计、实现和验证。”
- 希望多方分工检查：“用多agent按这份需求完成实现和独立审查，连续做完后统一交付。”

把材料发来，说明目标即可；我先读已有项目约定，继承已知范围和授权。真正缺少且影响正确性的业务决定或操作范围，才用业务语言问你。只想分析就说“只看不改”；只要需求就说“先做到需求”；允许完成本地成果就说“做完并验证，先不提交、不推送”。不需要记住内部终点值。

## 分工与能力

| 角色 | 职责 |
| --- | --- |
| 主代理 | 整理完整任务、继承要求、安排技能/代理、核对证据、统一交付 |
| 执行者 | 完成当前阶段的业务总结、需求、设计、实现或文档，并验证成果 |
| 独立审查者 | 对照原始材料独立推导预期，检查成果、反例和实际输出，反馈有证据的问题 |
| 按需探索员 | 只读调查具体未知事实；已有证据足够时省略 |

普通工作流由当前代理按阶段使用同样的需求、设计、技术和测试skills。多agent时把相关技能及原材料交给对应角色，不强制每阶段新开代理。角色名称不证明实际使用技能：读取轨迹、采用规则与成果位置会留在已有记录，交付可回查。

## 交叉检查及交付

执行者完成一个可审查版本，另一名代理根据原材料和验收独立判断，不只看作者自评。发现问题后，执行者根据证据局部纠正，复核受影响部分；主代理核对最终候选。普通独立审查不自动等于盲审；要求隐藏答案时还要检查可见上下文。

结束时你会看到：完成了什么、实际有哪些角色参与及使用什么能力、审查发现和纠正、验证结果与未验证项。没有实际派发或技能不可用时会如实说明，不把计划当执行，不用当前代理自查冒充另一位审查者。必要独立审查缺失时相应验收仍未满足。

## rc.17：反馈怎样变成改进

你照常指出问题即可，不需要填写反馈表或多走审批。助手先修当前成果，并在原任务记录中保留问题、影响版本和复验结果。同一消息的转发不重复计数；后续收到反馈、恢复相关任务或进行同类交付时，再核对问题是否复发。没有实际使用反馈，不会因为测试通过或无人回复就写成“用户认可”；也不会为等反馈卡住已授权交付。

修改技能前先找已有规则：已有要求足够就纠正执行，确有缺口才合并、替换或新增。共性要求保留一个权威位置，入口引用；不会在每个技能复制同一句话，也不为此新建后台扫描服务。正式技能修改仍须具备相应授权，普通反馈本身不代表允许安装或替换技能。

这延续了rc.16的独立入口与交付阅读检查，并保留rc.15的专家更新。`product-manager`的上游内容仅限已确认的非商业用途，商业使用需相应许可或合规替代，见[许可说明](../outputs/company-codex-workflow-v2-zh/skills/product-manager/PROVENANCE.md)。

## 中途可以改变选择

说“改用多agent”即可表达协作意愿；说“后面由你一个做，不用多agent”会停止新派发，核对已派工作实际停止、保留有效成果后接续。停止状态不能仅凭代理回复判断，不能直接重派造成重复执行。说“暂停”则停止推进，等待你恢复。

选择只作用于当前请求及明确约定的范围，不自动变成所有新项目的永久设置。任何方式都沿用相同业务范围和质量要求，不自动包含提交、推送、合并、部署或生产操作。多agent增加独立判断，但不保证更快，也不承诺更换了模型。

若当前会话没有子代理工具，会明确说明，继续可独立完成的已授权工作；不会宣称完成了多agent协作。这里没有新增按钮、slash命令或常驻后台系统。详细操作和能力映射供需要时查阅：[多 Agent 交付规则](../outputs/company-codex-workflow-v2-zh/skills/company-expert-routing/references/multi-agent-delivery.md)。
