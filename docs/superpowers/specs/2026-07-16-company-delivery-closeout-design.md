# Company Delivery Closeout Design

**日期：** 2026-07-16
**状态：** 已确认设计，待实施计划
**目标：** 为公司工作流增加独立的交付收口能力，在任务批次、功能或里程碑全部完成后，规整代码与文档成果，安全清理临时文件，完成最终验证、代码审查、本地提交并推送当前业务分支。

## 1. 问题与原则

现有 `company-implementation-runner` 负责逐项实现和验证，但不负责多个任务完成后的整体交付。缺少独立收口层会导致文档状态、任务状态、临时文件、验证证据和 Git 操作分散处理，也容易出现“代码完成但成果没有整理”的情况。

设计遵循以下原则：

- 任务完成不等于里程碑可交付；必须在最终待提交状态上重新核验。
- 收口应可重复、可审查、按风险停止，不能成为自动删除和自动推送的黑盒。
- 用户说“开始交付收口并推送业务分支”即授权普通本地 commit 和普通 push；不授权 force、rebase、amend、合并、发布或部署。
- 默认不新增重复文档，优先更新项目已有权威文档和任务状态。
- 只自动清理来源明确且可证明由当前任务产生的临时文件；来源不明文件必须暂停确认。

## 2. 能力边界

新增双语 skill：

```text
company-delivery-closeout
```

适用范围：

- 已完成的任务批次。
- 已完成的 feature。
- 已完成的里程碑或版本阶段。

不负责：

- 继续实现未完成任务。
- 自行补写未确认需求或业务规则。
- 部署、发布、合并主分支或创建 PR。
- 改写 Git 历史、force push 或删除来源不明文件。

## 3. 路由关系

`company-workflow-help` 在用户表示“全部任务完成”“整理本次成果”“清理临时文件并提交”“收口并推送”时路由到本 skill。

`company-implementation-runner` 在任务清单全部完成且没有下一批实现任务时，下一步必须推荐 `company-delivery-closeout`，不得只输出普通完成报告。

收口 skill 组合而不重写以下能力：

```text
company-delivery-closeout
-> company-expert-routing（仅复杂领域审查需要时）
-> superpowers:requesting-code-review（L2/L3 或非平凡代码交付）
-> superpowers:verification-before-completion（所有正式交付）
-> superpowers:finishing-a-development-branch（Git 收尾判断）
```

## 4. 执行模式与授权

支持三个模式：

| 模式 | 行为 |
| --- | --- |
| `prepare` | 盘点、规整、清理计划、验证和交付报告，不 commit、不 push |
| `commit` | 完成收口并创建本地 commit，不 push |
| `deliver` | 完成收口、本地 commit，并普通 push 到当前业务分支 |

自然语言默认映射：

- “开始交付收口” -> `prepare`
- “收口并提交” -> `commit`
- “收口并推送业务分支” -> `deliver`

本设计确认的公司默认入口为：

```text
所有任务已完成，开始交付收口并推送业务分支。
```

该口令一次性授权 `deliver`，正常路径中不重复询问；只有命中停止条件才暂停。

## 5. 七阶段收口流程

### 5.1 范围与分支门禁

- 确认项目根目录、当前分支、上游分支和里程碑/feature 权威任务文档。
- 禁止默认向 `main`、`master`、`develop` 或项目定义的集成分支执行 deliver。
- 核对任务项属于已完成、明确延期或明确不做；不得静默关闭未完成任务。
- 明确本次允许纳入提交的目录、文件和现有用户改动。

### 5.2 成果盘点

使用稳定、只读的 Git 状态和 diff 命令盘点：

- 正式代码、测试、配置和迁移。
- requirements、business rules、design、API contract、tasks、入口索引和 lifecycle 文档。
- 合法生成物和需要保留的交付资产。
- 临时文件、缓存、截图、验证报告和运行产物。
- 来源不明、范围外、大体积、二进制或疑似敏感文件。

所有文件必须分类后才能进入暂存清单。不得直接使用 `git add .`。

### 5.3 文档与成果规整

- 核对需求、设计、业务规则、任务状态、代码行为和验证证据的一致性。
- 同步项目已有的 `说明文档.md`、`specs/global/INDEX.md`、当前 version/feature README、任务文档和 lifecycle 记录；仅更新项目实际存在且承担对应职责的文件。
- 清除失效入口和错误完成状态，但保留有审计价值的历史记录。
- 代码格式化、注释和文档调整必须与本次交付直接相关，不做邻近重构。

### 5.4 临时产物清理

临时文件分三类：

1. **可自动清理：** 当前工作流明确创建、有路径记录、且不属于正式产物的截图、临时报表、测试输出或缓存。
2. **建议忽略：** 会重复产生且不应入库的文件；先建议加入项目 `.gitignore`，不得擅自修改全局 ignore。
3. **必须确认：** 来源不明、可能包含用户工作、数据库、附件、设计资产、日志证据或嵌套仓库的文件。

清理前必须先执行 dry-run。禁止使用无范围的 `git clean -fdx`。删除后重新盘点并报告删除清单。

### 5.5 最终验证与代码审查

- 根据最高风险任务确定最终 `V0/V1/V2/V3` 验证等级，不得因单项任务曾通过而跳过整体门禁。
- 执行相关测试、类型检查、lint、构建、必要浏览器/E2E 验证和 `git diff --check`。
- L2/L3 或包含非平凡代码时执行代码审查；审查范围是最终待提交 diff，而不是对话描述。
- 检查疑似密钥、生产配置、数据库文件、超大文件和意外依赖变更。
- 所有完成声明必须基于本轮新鲜证据。

### 5.6 Commit 与 Push

验证通过后：

1. 展示最终文件清单、diff 统计、删除清单、验证证据、未验证项和建议提交信息。
2. 只暂存已确认分类的具体文件。
3. 再检查 staged diff，确认没有遗漏或混入范围外文件。
4. 创建一次本地 commit，并记录 commit SHA。
5. `deliver` 模式使用普通 `git push -u origin HEAD` 推送当前业务分支。

禁止自动执行：

- `git add .`
- `git reset --hard`
- `git push --force`
- rebase、amend、branch delete、merge、release 或 deploy

### 5.7 交付报告

最终报告必须包含：

- 工作流层与执行模式。
- 收口范围、任务完成状态和权威文档。
- 代码、测试、文档、配置和资产成果。
- 已删除临时文件、已保留候选文件和新增 ignore 建议。
- 实际调用的 Superpowers、专家和审查能力。
- 验证等级、命令、结果和未验证项。
- commit SHA、业务分支、远端和 push 结果。
- 剩余风险、延期事项和下一步建议。

## 6. 停止条件

命中任一条件必须停止，不得 commit 或 push：

- 当前位于受保护的主分支、开发分支或集成分支。
- 任务未完成且没有明确延期/不做决定。
- 发现来源不明、范围外或可能属于其他用户/对话的修改。
- 删除候选无法证明是当前任务临时产物。
- 测试、构建、关键浏览器验证、代码审查或安全检查失败。
- 文档与代码的当前状态仍然冲突。
- 存在疑似密钥、数据库文件、生产配置或意外大文件。
- staged diff 与确认清单不一致。
- 远端分支领先、普通 push 被拒绝，或需要 rebase/force 才能继续。
- 网络、权限或远端状态无法确认。

停止输出必须说明：阻塞项、已完成的安全步骤、未执行的 Git 动作和恢复入口。

## 7. 自动化边界

第一阶段只实现 skill 编排，复用项目已有测试、构建和 Git 命令，不新增通用清理脚本。

经过 2-3 个真实项目验证后，如果临时文件模式、检查命令和停止条件稳定，再考虑增加：

- `scripts/closeout.sh`
- `scripts/closeout.ps1`
- 项目级 closeout 配置和机器可读报告

脚本只承担确定性检查和 dry-run，不承担文件归属、需求完成或风险授权等语义判断。

## 8. 验收标准

- 用户不记 skill 名也能通过自然语言进入收口。
- `prepare`、`commit`、`deliver` 三种模式边界明确。
- `deliver` 正常路径一次授权即可完成本地 commit 和普通业务分支 push。
- 来源明确的临时文件能安全清理；未知文件不会被删除。
- 最终待提交状态经过文档一致性、验证、审查和敏感信息检查。
- 不使用无差别暂存、破坏性清理、历史改写或 force push。
- commit/push 失败时不虚假报告成功，并保留可恢复状态。
- 中英文公司插件行为一致，中文本地安装后可通过 `/company-delivery-closeout` 入口使用。

## 9. 外部实践依据

- Git `git-clean`：清理前使用 dry-run 或交互模式，删除操作默认需要 force。
- Git `git-status --porcelain`：为自动化提供稳定的工作区状态格式。
- GitHub protected branches、required checks 和 reviews：交付前使用可执行门禁，而非只依赖完成声明。
- GitHub push protection：阻止密钥被推送到远端。
- Google Engineering Practices：代码、测试、文档和审查应作为同一变更的完整质量边界。
- Google SRE Release Engineering：发布流程应可重复、自动化，并在实际发布版本上重新测试、记录变更和保留审计轨迹。
