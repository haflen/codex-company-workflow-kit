# Pilot Playbook

这份手册用于公司内部试点。目标是在一个真实项目里验证工作流是否提升交付稳定性，而不是一次性强推到所有团队。

## 试点范围

建议选择：

- 一个中等复杂度 feature。
- 一个真实 bugfix。
- 一个可选 spike 或 hotfix 演练。

暂不建议选择：

- 跨多个系统的大型重构。
- 尚未明确业务目标的长期项目。
- 高风险线上事故的第一次真实处置。

## 参与角色

- 业务/产品确认人：确认需求和验收标准。
- 技术负责人：确认设计、边界和风险。
- 实现人：使用 Codex 执行任务。
- Reviewer：检查输出、验证证据和流程负担。

## 第一个 Feature 怎么跑

1. 业务用户说：`帮我梳理这个功能需求：...`
2. 需求确认后说：`需求已确认，进入技术设计`
3. 技术负责人确认设计后说：`方案已确认，进入任务拆解`
   - 如果需求路径、方案路线或旧项目边界仍不清楚，先让 Codex 输出 `Codex 计划模式建议`；命中建议或强烈建议时，先用计划模式判断路线，不改文件、不编码。
   - 任务拆解时检查是否输出 `Subagents 建议`、`Subagent 能力状态` 和每个任务的 `Subagent 策略`；小任务可以不用，但复杂任务应说明为什么建议或不建议。
4. 实现人确认任务后说：`任务已确认，开始实现`
   - 如果任务清单已经完整确认，并且希望 Codex 连续推进多个低/中风险任务，可以说：`任务已确认，连续完成后续所有可执行任务；遇到范围变化、V3 风险、验证失败或需要我确认时再停。`
   - 如果这是跨阶段或跨会话 feature，让 Codex 输出 `目标追踪建议`，必要时建立 Codex 目标记录最终成功标准。
   - 如果实现报告出现 `Subagents 实际调用：已调用`，Reviewer 要检查主 agent 是否复核了子 agent 的 diff、验证证据、文档漂移和剩余风险。
   - 如果实现报告写 `需要本地 custom agents 配置`，先执行 `bash scripts/install.sh install-agents <project-path> --lang zh`，再决定是否显式请求 subagents。
5. 完成后要求 Codex 输出：
   - 变更总结
   - 文件变更
   - 验证命令或手工验证
   - 剩余风险
   - 下一步建议和推荐用户下一句
   - 目标状态建议，如是否继续保持或关闭 Codex 目标

## 第一个 Bugfix 怎么跑

1. 用户说：`开始 bugfix：...`
2. Codex 先判断 bug 还是需求变更。
3. Codex 复现或收集证据。
4. Codex 做最小修复。
5. Codex 输出根因、修复、回归验证。

## 试点验收指标

- 需求是否比以前更清楚。
- 设计和实现是否能追溯。
- 验证证据是否更完整。
- 简单任务是否没有被过度流程化。
- 专家技能是否在合适节点自动参与。
- Codex 计划模式是否只在不确定路线或高风险任务中建议使用，没有变成全量强制。
- Subagents 是否只在独立任务、独立失败域或高风险审查中建议使用；如果真实调用，是否有用户显式请求和主 agent 复核。
- 团队是否能接受新增文档成本。

## 试点结束复盘

建议复盘以下问题：

- 哪些唤起语最常用？
- 哪些节点太重？
- 哪些专家 bundle 缺失或误触发？
- 哪些模板字段没人填？
- 是否可以进入第二个项目试点？
